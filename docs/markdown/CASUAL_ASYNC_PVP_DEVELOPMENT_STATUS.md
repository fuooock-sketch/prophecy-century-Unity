# 异步 PVP 开发与验收进度

更新时间：2026-09-12。

## 目标与工作边界

以现有异步镜像原型为基础，完成可连续游玩的休闲对战模式，再进入远端小规模试玩。
保留已确认规则：100 生命、同回合匹配、锁阵后展示对手、15 回合结束或无尽、3 个独立存档槽。
现有文件或方法仅代表已有实现，不代表通过玩法验收。

## 第二批交付：锁阵、断点恢复与结算

已实现：

- 回合结束保存已结算回合、己方镜像和 `casual_locked` 状态；恢复不重复触发回合结束成长。
- 匹配完成后保存对手与匹配 ID；已锁定对手直接恢复，不重新匹配。
- 经营命令入口拒绝锁阵后的购买、出售、部署、换位、刷新、升级、锁店与使用宝钻。
- 所有读档入口恢复匹配流程、第 15 回合选择或终局页；读档与返回标题停止旧播放协程。
- 战斗预览和正式模拟在独立进度副本上运行，播放期间保存战前检查点；播放完成后同步提交副本、流程结算和存档。
- 重复结算回调被拒绝；保存失败提供重试，不继续推进战斗或重复应用里程碑选择。
- 修复 Unity 将空镜像反序列化为空对象导致里程碑错误恢复成匹配的问题；旧存档阶段转换之后再恢复 PVP 锁阵状态。
- 副本保留空商店位和空奖励，避免序列化改变经营结构。

验证结果：2026-09-12 当前代码通过运行时 C# 编译、独立 Unity 恢复自测，日志包含 `Casual PVP recovery checks passed` 和 `Casual PVP self test passed`。
验证方式：运行 `powershell -NoProfile -ExecutionPolicy Bypass -File tools/validate_casual_pvp.ps1`。脚本使用 Unity 2022.3.62f3c1 配套 C# 编译器和当前项目引用参数编译运行时代码，在 `tools/obj/PvpRecoveryValidation` 独立 Unity 项目执行 `CasualPvpSelfTest.RunBatch`，检查本次新日志中的成功与异常标记。
测试目录不再使用 Unity 的 `Temp`，避免主编辑器退出时清理测试文件。
测试使用实际游戏数据、实际战斗系统和临时休闲存档槽，涵盖锁阵命令、重复回合结束、读写恢复、战斗隔离与重算、空商店位与空奖励、重复结算、15 回合结束/继续与零血终局。
编辑器内也可通过 `Tools/Prophecy Century/Run Casual PVP Self Test` 运行；恢复测试临时替换会话，结束后恢复原会话。

边界：本批验证的是运行时逻辑和真实序列化，没有完成主界面逐步点击、战斗中强制退出的端到端测试，也没有验证真实磁盘写入故障。Windows 自动化工具初始化失败（缺少 sandboxPolicy 元数据），因此改用独立批处理项目，不操作用户当前 Unity 场景。

下表保留第一批发现的原始缺口，前四项已有上述实现和逻辑回归，仍需完整界面验收；最后一项上报队列在第三批实现。

初始问题与验收方向：

| 优先级 | 问题与证据 | 修复及验收方向 |
| --- | --- | --- |
| P0 | `PlayBattleStage` 在匹配完成后保存，但此时尚未执行 `SetBattlePhase`，存档仍可能为经营状态；读档入口直接打开经营界面 | 持久化锁阵阶段、己方快照、对手和匹配 ID；恢复后禁止购买、出售、换位和重新匹配 |
| P0 | `PlayBattleStage` 每次进入都会调用回合结束效果，已有对手分支没有跳过该调用 | 用持久化阶段保证回合结束结算只执行一次；匹配前后退出均不重复成长 |

| P0 | 战斗模拟会修改运行状态，而流程结算和持久化发生在播放之后 | 明确战前检查点、结算提交和表现之间的关系；战斗中退出不能重复扣血或获得奖励 |
| P1 | `ReportBattle` 发送后未保留失败队列 | 保存待上报结果，网络恢复后使用相同匹配 ID 重试；本地保底结果不冒充服务器匹配 |

## 第三批交付：镜像属性与战绩队列

镜像更新：

- 攻击包含经营阶段 `boardAuraAttack`；还原增量允许低于基础值，避免镜像属性被错误抬高。
- 新镜像保存本队累计赐予、单位收到/附着宝钻计数和战斗进度计数。
- 敌方及其召唤物使用镜像所属队伍的累计赐予，不借用当前玩家数据。
- 每单位生命字段按当前战斗引擎实际使用的 `hpPerUnit`/`hp` 捕获；本批不修改引擎对永久生命成长的整体规则。
- 使用 `battle_v2` 匹配池；历史日志仍标记 `battle_v1`，缺少新字段的数据不作为 v2 完整镜像。旧数据仍保留。
- 服务端保留并验证新增计数，去重键包含队伍计数；客户端拒绝未知单位、非法/重复站位以及自身镜像响应。

结果同步：

- 战绩先加入本局待发送队列，再与回合结算一起写入存档；记录原服务器地址和匹配 ID。
- 本地保底及没有已知服务器来源的旧匹配不进入远端上报队列。
- HTTP 成功且响应明确 `success: true` 才移除；服务器的重复上报成功确认同样有效。
- 失败保留队列、尝试次数及错误；客户端非战斗播放时每 30 秒尝试，单批最多 5 条，优先尝试次数少的记录。
- 切换进度后旧请求不修改新进度；读档/返回标题重置发送协程状态。发送成功后的本地保存失败允许读档后再次发送，由服务端幂等保护。

验证：Python 服务端 14 项测试通过，新增 v2 字段往返、计数去重与缺字段拒绝；Unity 自测新增真实双方初始属性对比、敌方计数归属、队列真实存档读写、失败保留及成功确认移除。
边界：第三批队列测试验证状态、序列化和响应判定，真实 HTTP 故障联调在第四批完成。队列随所属存档保存，删除该存档也会删除其待发送记录。

## 第四批交付：真实 HTTP 联调与对手确认

- 实际上传与同回合匹配通过，返回对手来自其他测试局。
- HTTP 503 后结果保留并写入真实临时存档；恢复正常响应后移除队列且落盘。
